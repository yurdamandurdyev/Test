# Telegram assistant · v2

## Сценарий

`/start` → короткая инструкция → CSV → одно сообщение «Проверяю…», которое заменяется сводкой. Ничего не отправляется автоматически в виде технической таблицы. Шесть inline-кнопок: обзор, источники, бюджеты, качество и дубли, PDF, CSV. Разделы меняют существующее сообщение. Файлы появляются только по запросу. Для повторной загрузки в течение 10 минут предлагаются кнопки уже созданного отчёта.

Основной файл — векторный PDF A4, обычно три страницы: обзор и источники; бюджеты; проверки CRM и методика. Длинный материал переносится на дополнительную страницу. Графики построены из текущего отчёта, без изображений из сети. Светлая печатная палитра, типографика и приглушённый зелёный согласованы с Signal. Отдельная PNG-карточка сознательно не добавлена: краткое сообщение уже даёт пересылаемую сводку; картинка дублировала бы её и увеличивала число сообщений.

CSV по кнопке — все строки и русские пояснения. Машинный `export_csv` и автономный скрипт сохраняют прежний контракт и коды. Формулы экранируются обоими экспортами.

## Разделение ответственности

- `analytics.py` не изменён. Один analyze(bytes) для CLI, сайта, polling и webhook.
- `presentation.py`: форматирование, объяснения, кнопки, человекочитаемый CSV.
- `report_pdf.py`: ReportLab + встраиваемые DejaVu Sans; без Chromium, subprocess или временных CRM-файлов. Шрифты и лицензия входят в пакет.
- `webhook.py`: получение файла, проверка доступа, распределённое состояние, callbacks и повторная доставка.
- `bot.py`: тонкий polling-адаптер того же обработчика. Для интерактивного polling теперь также нужен существующий Redis; одновременный запуск с webhook запрещён.

## Состояние и безопасность

Redis хранит только случайно выглядящий HMAC report_id, владельца, chat_id, Telegram file_id и SHA-256 файла. Ни CSV, ни имена, телефоны или полный JSON отчёта не сохраняются. TTL отчёта — один час, без продления при нажатиях. На каждом callback проверяются текущий allowlist, личный чат и владелец. Просроченная кнопка объясняет необходимость повторной загрузки. Сам файл повторно получается из Telegram и анализируется тем же ядром; digest проверяется перед выдачей.

callback_data — строго `r:<24 hex>:<разрешённое действие>`, меньше 64 байт. Пути/URL/данные файла в callback не входят. HTML экранируется, отображаемый текст ограничен по UTF-16 после разбора HTML. Неизвестные источники не превращаются в разметку. PDF получает экранированный текст, не HTML пользователя. В логах только фиксированные технические события, без входных данных, Telegram URL и исключений транспорта.

TTL блокировки — 90 секунд; защита от повторной обработки файла — 10 минут; receipts update_id — 7 дней. Два запроса одного пользователя не обрабатываются параллельно. Callback при занятости получает предложение повторить нажатие. Повтор одинакового update_id не отправляет результат снова. Скачивание одного формата одного отчёта ограничено одним запросом за 30 секунд (в том числе при неопределённом результате отправки).

При ошибке доставки Telegram получает 503; после трёх неудачных попыток обработки следующий retry отмечает обновление завершённым и по возможности объясняет пользователю, как повторить действие. Сбой Redis до счётчика не позволяет применить этот предел, но и отчёт в такой ситуации не отправляется. Полную exactly-once гарантию между Telegram и Redis обеспечить нельзя: потеря ответа после отправки до сохранения receipt оставляет небольшое окно повторной доставки. Оно ограничено блокировками и числом попыток; не обещается невозможное.

Файлы и ответы в Telegram остаются до удаления пользователем. Удаление Redis-состояния не удаляет сообщения Telegram. Ссылка на публичный отчёт не создаётся.

## Что означает сводка

8 заявок, 6 разных распознанных телефонов и 7 заявок при гипотетическом удалении полного совпадения — разные показатели. Основной результат сохраняет все строки. Нормализованный телефон — приближение к контакту, не доказательство личности. Дубли определяются прежними правилами; повторные обращения по телефону в разные даты сохраняются.

Временные показатели: последний корректный день и семь дней по него включительно. Качество и распределение бюджетов: весь файл, подписи явно это сообщают. Нули входят в средний бюджет, пропуски и ошибки исключаются. Нет утверждений о конверсии, выручке и эффективности рекламы. Рекомендации детерминированные: проверить конкретные замечания и номера записей.

## Обновление существующего Production

1. Дождаться Vercel deployment нового main. `/api/health` должен содержать `telegram_ui_version: "2.0.1"`. Новых серверных переменных и сервисов не требуется.
2. **Повторно зарегистрировать webhook** обновлённым скриптом, чтобы Telegram доставлял `callback_query` наряду с `message`. Токен и webhook secret читать только из защищённого окружения:

```bash
.venv/bin/python scripts/telegram_setup.py register
.venv/bin/python scripts/telegram_setup.py status
```

3. В статусе должно быть `Callback delivery enabled: True`. Без повторной регистрации уже установленный webhook может продолжать принимать только файлы и игнорировать кнопки.
4. Отправить `/start` и исходный CSV: одна компактная сводка, 8 заявок за неделю, 3 за день, 6 разных телефонов за неделю, средний 6 916 666,67 ₽.
5. Открыть все четыре раздела. «Качество»: группа возможного дубля — записи 1,2; бюджеты отсутствуют у 4,6; нули у 3,8. Альтернатива — 7 заявок, средний 5 900 000 ₽ за неделю.
6. Скачать PDF (открыть кириллицу и три страницы), затем CSV (8 записей, русские замечания). Дважды быстро нажать скачивание: один файл и понятный toast. Через 30 секунд файл можно запросить снова.
7. Проверить другой разрешённый аккаунт на чужом report_id (отказ), запрещённый ID, групповой чат, некорректный CSV. Через час кнопки просят повторить загрузку. Файл при ошибках не должен создавать бесконечный поток сообщений.
8. Vercel → Logs → Production → `/api/telegram/webhook`; фиксированное событие `telegram_delivery_failed` без секретов. `getWebhookInfo` показывает очередь и наличие исторической ошибки, не полный диагноз. Проверяйте, уменьшается ли очередь после новых успешных запросов.

## Проверки этой итерации

Локальный benchmark на исходном наборе: PDF около 58 КБ, ~0,04 с. Синтетический файл 10 000 строк (726 731 байт): analyze ~0,21 с, PDF ~0,04 с, пиковый RSS процесса ~67 МБ. Это измерения локального процесса; сетевое время и cold start Vercel в них не входят. Векторный PDF не запускает браузер. Проверены A4, встроенная кириллица, текстовые границы страницы и визуальные рендеры.

Реальная приёмка нового сценария требует обновлённого Production, регистрации callback_query и действий пользователя в Telegram. Предыдущее успешное получение CSV подтверждено пользователем; это не выдаётся за проверку новой версии.

Локальная приёмка перед публикацией: 92 Pytest, 3 Vitest, 8 Playwright; production build прошёл. pip-audit runtime-зависимостей: известных уязвимостей не найдено. Проверка PDF: 467 текстовых фрагментов, ни одного за границами страницы. Проверка автономных HTML: 0 сетевых запросов, 0 ошибок браузера. git diff подтверждает неизменность analytics.py, автономного Python-скрипта и памятки задания 3. Публикация и реальный Telegram нового сценария отмечаются отдельно после выполнения.

## 2.1 · Транскрипции звонков

`/start` открывает меню CRM / звонки / помощь. CSV работает без выбора режима. TXT (UTF-8, до 2 МБ) и текст с ролями М:/К: передаются напрямую в `transcripts.documents_to_calls`; веса и расчёты не копируются. Несколько звонков в TXT разделяются строками «Звонок 1», «Звонок 2». Ожидаемый ЖК по умолчанию совпадает с вебом — Северная Гавань; `/project Название` задаёт его для новых отчётов на час. Существующий отчёт сохраняет своё значение.

Кнопки: сводка (по пять звонков), звонок, критерий с пагинацией, рекомендации, PDF/CSV. «Не выполнено» и «Требует проверки» пересчитывают отчёт; «Подтвердить» запрашивает точную цитату через ответ на сообщение бота, допускает строку «Причина: …». `/cancel` отменяет ввод. Проверяются принадлежность цитаты исходнику, владелец и личный чат. Неопределённые баллы остаются null. Для исправления ролей/статуса разговора в MVP нужно поправить TXT и отправить заново; редактирование метаданных в чате не добавлено.

Redis: для TXT сохраняется file_id + digest, для обычного сообщения — текст; также ручные решения и срок истечения. Всё удаляется по TTL не позднее часа после создания; ручная проверка срок не продлевает. Ключи завершённых update/progress содержат только идентификаторы и истекают по прежним правилам. Содержимое не журналируется. Дедупликация 10 минут, ограничение повторной выгрузки 30 секунд, общий user-lock и ограниченные повторы webhook сохранены. Telegram хранит саму переписку независимо от TTL Redis.

PDF использует существующие ReportLab, шрифты и палитру; длинные цитаты явно сокращены до 700 символов. CSV — тот же полный экспорт критериев, что на сайте. Новых зависимостей, сервисов и секретов нет; webhook и разрешённые ID не перенастраиваются. Версия в `/api/health`: `telegram_ui_version: 2.1.0`.

Проверено локально: 144 Pytest, 3 Vitest, 10 Playwright, build. Есть тест полного совпадения Telegram-отчёта с веб-API, TXT/текста/CSV, ручной проверки, пагинации, разделения доступа, TTL, повторов и экспорта. PDF проверен извлечением кириллицы, A4, границ слов и визуальным просмотром. Живой Telegram Bot API этим прогоном не проверялся: секреты бота в рабочей среде отсутствуют.
